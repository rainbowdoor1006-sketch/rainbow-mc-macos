# RAINBOW MC · 「万物皆插件」方案对比

> 目标：让启动器的功能可以像 DeepSeek Harness 那样由插件扩展（甚至核心功能也走插件）。
> 本文只做方案对比与风险评估，不含实现代码。

---

## 零、先定一件事：插件化的**范围**

这一条决定了后面所有成本。

| 范围 | 含义 | 后果 |
|---|---|---|
| **A. 全插件化（Core 极简）** | 主程序只留「窗口 + 插件宿主 + 数据目录」，版本管理、下载、启动、整合包、联机全部做成官方插件，用同一套 API | 架构最干净、第三方能做任何事；但要把现有 20+ 模块整体重构，启动链路多一层边界（+100~300 ms），关键路径出问题排查变难。工期 2~3 周起 |
| **B. 混合（Core 保留关键路径）** | 启动、下载、实例、更新留在 core（性能与稳定性优先）；插件扩展「页面 / 资源源 / 整合包格式 / 诊断规则 / 主题 / 命令」 | 成本可控（3~7 天到能用），风险集中在外围；缺点：core 里有硬编码，日后想全插件化要再拆一次 |
| **C. 仅外围扩展** | 只允许加页面、加按钮、加主题、加下载源，完全不碰启动流程 | 最安全、最快（1~2 天），但「万物皆插件」名不副实 |

> 我的判断：先做 **B**，把 API 设计成「未来能拆 core」的形状（关键路径也走同一套接口，只是内置实现），这样以后想做 A 不用推翻。

## 一、沙箱模型（插件在哪里跑）

| 编号 | 模型 | 能力 | 安全 | 性能 | 工期 |
|---|---|---|---|---|---|
| **S1** | **进程内**（main 里 `import` 插件，完整 Node 权限） | 全部 | ❌ 极低（插件=病毒） | 最好 | 1 天 |
| **S2** | **utilityProcess / 子进程 + RPC**（后端逻辑在独立进程，fs/net 通过宿主 API 代理） | 高 | ⭐ 中（可限制、可杀、崩溃隔离） | 好 | 3~5 天 |
| **S3** | **S2 + 渲染层 iframe**（UI 用 iframe + postMessage，禁 nodeIntegration） | 高 | 中高 | 好 | 5~7 天 |
| **S4** | **QuickJS / WASM 沙箱**（插件只能调白名单 API，无原生 fs/net） | 中 | ⭐ 高 | 中（有序列化开销） | 7~10 天 |
| **S5** | **纯声明式**（JSON/YAML 配置，无代码，只能组合已有能力） | 低 | ⭐ 极高 | 最好 | 1~2 天 |

### 各自的硬伤

- **S1**：插件 `require('fs').rmSync('C:/')` 就没了。学生用户会装「免费光影插件包」，这就是分发病毒的通道。
- **S2**：进程边界带来 IPC 序列化成本；插件要读大文件（整合包）要设计流式接口，否则内存翻倍。
- **S3**：iframe 里跑 React 插件需要打包约定（单文件 bundle + 全局注册函数），开发体验比原生差一截。
- **S4**：生态门槛高——大部分社团同学写不了 WASM/受限 JS，插件数量会很少。
- **S5**：做不了「新页面」「新下载协议」这类真正的扩展。

> 推荐组合：**S3（= S2 + iframe）**。安全与能力平衡，且和 VS Code / Obsidian 的心智模型一致，用户容易理解「插件可能要求权限」。

## 二、扩展点（插件到底能改什么）

分四档，从安全到危险：

| 档位 | 扩展点 | 例子 | 风险 |
|---|---|---|---|
| **L1 展示类** | 主题/配色、字体、i18n 语言包、启动画面、侧栏图标 | 「暗色-紫罗兰主题包」 | 低（最多丑） |
| **L2 信息类** | 启动前预估规则、崩溃诊断规则包、模组简介来源、日志解析器 | 「整合包作者写的诊断规则包」 | 低（只读日志） |
| **L3 数据类** | 下载源 provider（CurseForge 镜像、自建 CDN）、整合包格式解析器、组件库条目类型 | 「BBSMC 汉化补丁源插件」 | 中（能往磁盘写文件） |
| **L4 行为类** | 启动前/后钩子（改 JVM 参数、注入文件、拉起进程）、命令面板动作、托盘行为 | 「性能优化插件：自动加 XX:+UseZGC」 | 高（等于任意代码执行） |

**必须先划的线**：
- L4 只对「已签名/白名单」插件开放，或安装时强制二次确认 + 橙色警告
- 插件**永远不能**读写 `config.json` 里的账号令牌（哪怕 S1 也不给，走 API 也不暴露）

## 三、分发方式

| 编号 | 方式 | 优点 | 缺点 |
|---|---|---|---|
| **D1** | 本地目录（`data/plugins/<id>/`），手动放 | 零成本 | 用户不会用 |
| **D2** | 手动导入 zip（拖拽到窗口） | 简单、可控 | 仍要自己找插件 |
| **D3** | **自建在线索引**（`https://rainbowdoor.icu/api/plugins/index.json` + sha256 + 签名） | 有市场感、可审核、可统计 | 要维护服务端与审核流程 |
| **D4** | GitHub 直装（填 `owner/repo`，拉 Release） | 零服务端成本、开发者友好 | 无法审核、sha 不可信 |
| **D5** | 内置官方插件（随安装包，可禁用） | 体验最顺 | 安装包变大，更新耦合 |

> 现实做法：**D1 + D2 起步，D3 是终态**；D4 只对开发者模式开放。

## 四、权限模型

| 编号 | 模型 | 说明 | 用户体验 |
|---|---|---|---|
| **P1** | 全有或全无 | 装插件=交出全部权限 | 简单但危险，等同 S1 |
| **P2** | **能力清单 + 运行时网关** | manifest 声明 `fs:games` `net:http` `ui:page` `launch:hook`，宿主每次调用校验 | 安装时列权限清单，像手机 App |
| **P3** | 每次敏感操作弹窗确认 | 最安全 | 烦，会劝退 |
| **P4** | 签名 + 官方审核白名单 | 市场内可信 | 审核工作量在你这 |

推荐 **P2 为基础**，L4 权限额外叠加 **P4**（或首次确认后记住）。

## 五、API 稳定性与契约

| 要点 | 做法 |
|---|---|
| 版本协商 | 插件 manifest 写 `engines: { rainbow: "^1" }`，不匹配直接拒绝加载并说明原因 |
| 类型分发 | 发一个 `@rainbowmc/plugin-api` 包（只有 `.d.ts`），插件作者 `npm i` 就有补全 |
| 弃用策略 | API 只增不改；废弃字段保留 2 个大版本，加载时打印警告 |
| 崩溃归因 | 每次插件调用打 trace id；崩溃时弹窗明确写「最近调用的是 X 插件的 Y」 |
| 自动禁用 | 同一插件连续 2 次导致启动失败 → 自动禁用并提示（救命机制） |

## 六、六种组合的整体评分

| 组合 | 能力 | 安全 | 工期 | 维护成本 | 适合场景 |
|---|---|---|---|---|---|
| S1 + A（全插件化 + 进程内） | ★★★★★ | ★ | 15~20 天 | 高 | 只给自己用 |
| **S2 + B + P2（混合 + RPC）** | ★★★★ | ★★★ | 7~10 天 | 中 | 想尽快有生态 |
| **S3 + B + P2 + D2/D3（混合 + 双进程 + 市场）** | ★★★★ | ★★★★ | 12~18 天 | 中高 | **推荐** |
| S4 + B（QuickJS 沙箱） | ★★★ | ★★★★★ | 20 天+ | 高 | 面向陌生用户分发 |
| S5 + C（声明式 + 外围） | ★★ | ★★★★★ | 3 天 | 低 | 只想做主题/规则包 |
| S3 + A（全插件化 + 双进程） | ★★★★★ | ★★★★ | 30 天+ | 很高 | 长期目标 |

## 七、风险清单（按严重程度）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **插件=病毒通道** | 学生用户辨识力低，「免费光影插件」「加速插件」是天然诱饵，装完盗号/挖矿 | 市场审核 + 签名 + L4 权限二次确认 + 不暴露账号令牌 API |
| R2 | **供应链攻击** | 插件自身依赖的 npm 包被投毒 | 禁止插件带 `node_modules`（打包成单文件），或锁定依赖哈希 |
| R3 | **外挂/作弊插件** | 插件改联机数据或自动瞄准，破坏公平，社团名声受损 | 联机模式禁用 L4 插件；服务端校验关键数据 |
| R4 | **崩溃归因困难** | 插件挂了用户怪启动器 | trace id + 自动禁用 + 「安全模式启动（禁用全部插件）」 |
| R5 | **性能倒退** | 进程内插件阻塞主进程 → 启动卡顿 | S2/S3 天然隔离；给插件调用设超时 |
| R6 | **兼容性债** | API 一改老插件全崩 | 版本协商 + 只增不改 + 弃用期 |
| R7 | **法律** | 插件内嵌盗版资源 / 违反 Terracotta AGPL | 市场条款禁止；AGPL 组件只允许调用不允许改 |
| R8 | **代码签名缺失** | SmartScreen 警告，用户以为有毒；插件加载 DLL 受策略限制 | 先做 OV 签名再说 L4 插件 |
| R9 | **数据迁移** | 插件直写 `data/` 结构，将来 schema 变了全废 | 插件只能通过 API 读写，禁直接碰 `config.json` / `library.json` |
| R10 | **维护精力** | 你 15 岁，插件市场要审核、要答疑，是持续负担 | 先只做本地/zip 安装（无审核）；市场等有人气了再说 |

## 八、我建议的三步走

**第一步（3~4 天，能自用）**
- 插件清单 `data/plugins/<id>/plugin.json`（id/name/version/engines/permissions）
- 宿主：S2（utilityProcess）+ 网关（只开 `fs:games` `net:http` `log`）
- 扩展点：L1 主题 + L2 诊断规则包 + L3 下载源 provider
- 插件管理页：启用/禁用/卸载/查看日志
- 安全：全部插件默认「不受信任」，L4 钩子暂不开放

**第二步（4~6 天，能给别人用）**
- S3：iframe UI 插件（新页面、侧栏卡片）
- L4 启动钩子 + 二次确认 + 安全模式
- zip 拖拽安装 + sha256 校验 + 版本兼容检查
- 崩溃归因 + 自动禁用

**第三步（5~8 天，有生态）**
- 自建索引 + 审核流程 + 签名
- 官方插件（把「整合包格式解析」「资源配置」这些拆成内置插件做 dogfooding）
- 视情况再决定要不要走到「全插件化」

---

## 九、我不建议现在做的事

```
❌ 直接全插件化（把启动链路也塞进插件边界）——启动慢 100~300 ms，排查成本翻倍
❌ 进程内加载（S1）——一旦有市场，必然出现恶意插件
❌ 一上来就做市场——没有插件时市场是空壳，审核是纯负担
❌ 让插件直接读写 data/ 下的 JSON——将来改 schema 会集体崩
```
