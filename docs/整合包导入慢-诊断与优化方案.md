# 整合包导入慢 · 诊断与优化方案

> 对象：`七七的小翔修仙世界低配版 0.2.100beta.mrpack`（355.67 MB）
> 启动器：0.2.76　日期：2026-10-29
> 状态：**仅诊断，未做任何修改**

---

## 一、这个包到底要下多少

| 项 | 数量 | 大小 |
|---|---|---|
| mrpack 内已打包的 overrides（配置/资源/部分模组） | 603 个文件 | ~355 MB（本地解压，不走网络） |
| index.json 里需要联网下载的文件 | **103 个** | **304.0 MB**（全部来自 `cdn.modrinth.com`） |
| 依赖 | Minecraft 1.20.1 + Forge 47.4.23 | — |

也就是说：**解压 355 MB 是本地磁盘活，下载 304 MB 才是网速活。**

---

## 二、实测数据（本机，2026-10-29）

### 2.1 到 cdn.modrinth.com 的带宽

| 并发数 | 总吞吐 | 说明 |
|---|---|---|
| 1 路 | **39–43 KB/s** | 单连接被限得很死 |
| 6 路 | 173 KB/s | 有提升但不成比例 |
| 16 路 | **569 KB/s** | 接近本机国际带宽上限 |
| 24 路（Node fetch，与启动器同路径） | 448 KB/s，**18 成功 / 16 中断** | 有约 40% 请求被断流 |

**结论：瓶颈是「到 cdn.modrinth.com 的国际带宽 + 单连接限速」，多连接能换带宽。**
按 0.45 MB/s 算，304 MB 至少 **11 分钟**；按当前实测 0.1 MB/s 算，要 **50 分钟**。

### 2.2 下载时启动器的实际状态

```
启动器进程到 146.75.45.242（cdn.modrinth.com）的已建立连接：7 条
整机下行：98 KB/s
```

24 并发却只有 7 条连接，说明大量 worker 正卡在「等待/重试」而不是在传数据。

### 2.3 镜像可行性

| 镜像 | 结果 |
|---|---|
| `mod.mcimirror.top/Modrinth/...` | 302 **跳回 cdn.modrinth.com**，无提速 |
| `cdn.mcimirror.top` | 无响应 |
| BMCLAPI | 不代理 Modrinth 的 CDN |

**目前没有现成的免费国内镜像可替。**

## 三、慢在哪（按影响排序）

### ① 失败重试轮只有 4 并发，而且不换源（最主要）

`instance.ts` 现状：

```ts
const failed = await downloadAll(tasks, { concurrency: 24, ... })   // 第一轮
doneBytes = totalBytes
onProgress?.({ stage: 'download', done: doneBytes, total: totalBytes })  // ← 进度条提前拉满
if (failed.length) {
  await downloadAll(failed, { concurrency: 4, signal })              // 第二轮：4 并发
}
```

- 实测 24 并发有约 40% 请求被断（CDN 断流/超时），这 40 个文件全部进入第二轮
- 第二轮 **4 并发**、**仍然用同一个 url**（`altUrls` 压根没用上）、超时还是 600 s
- 结果：进度条已经 100%，实际还在用 40 条里 4 条慢慢爬 → 用户看到的就是"卡住不动"

### ② 没有按文件分片，单文件被限速拖死

单连接只有 ~40 KB/s。包里有没有大文件？有：`alekiNiftyShips` 单文件 22 MB，22 MB ÷ 40 KB/s ≈ **9 分钟**（一个文件）。

### ③ 解压 100% 后的几秒空档

`extractPackContent` 会写 603 个文件（355 MB），写完后才构建下载任务。空档来自：

- 603 个新文件落盘后，**Windows Defender 实时扫描**逐个查（jar 尤其慢）
- 解压结束后才做 `tasks` 构建、`totalBytes` 汇总、动态 `import('./http')`
- 期间进度条停在 100%，界面无提示

### ④ 没有速率/剩余时间

界面只有字节进度，没有 MB/s 和 ETA，慢的时候用户无法判断"是在下还是卡了"。

### ⑤ 重复导入会整包重下

虽然有 `sha1 + size` 跳过逻辑，但没有做**单文件断点续传**（Range），大文件中断就得从头来。

## 四、优化方案（待批准，本次不动手）

### P0-1 重试策略重写

```
第一轮：concurrency 24，失败收集
第二轮：concurrency 12（不是 4）
        · 换 altUrls（forgecdn → modrinth → 其他）
        · 指数退避 1s → 2s → 4s
        · 单次超时 600s → 90s（快速失败，快速换源）
第三轮：仅对仍失败的文件，逐个串行重试并给出明确失败列表
```

预期：拖尾环节从 20+ 分钟压到 2~3 分钟。

### P0-2 连接池与分片

```
· 给 fetch 传 undici Agent：connections: 64、keepAliveTimeout: 30s
· 单文件 > 8 MB 时切成 4~8 个 Range 分片并行拉，读完拼接 + sha1 校验
```

依据：16 路 569 KB/s、单路 40 KB/s —— 分片能直接吃到这个倍数。
预期：大文件提速 2~4 倍，整体 304 MB 从 40~50 分钟降到 **10~15 分钟**（受国际带宽上限约束，不可能再快）。

### P1-1 解压后的空档

```
· 解压完成后立刻推一条「准备下载：103 个文件 / 304 MB」，别让进度条空着
· 解压改为分批 yield（每 100 个文件让出一次事件循环），避免界面卡死
· 提示用户：若杀软实时扫描开着，解压后会慢几秒（可把实例目录加白名单）
```

### P1-2 进度信息

```
· 显示「已下载 123 / 304 MB · 0.42 MB/s · 剩余约 8 分钟」
· 显示「重试中 3 个 / 失败 0 个」，让"卡住"可解释
```

### P2 体验

```
· 拖入 mrpack 后先解析 index，直接告诉用户「需额外下载 304 MB，预计 10~15 分钟」
· 重复导入时按 sha1 跳过已有文件（已有逻辑，需验证）
· 支持「走系统代理」开关（用户开了 Clash 时能显著提速，但这是用户侧条件）
```

## 五、给用户的诊断建议（自己就能验）

1. 打开任务管理器 → 性能 → 以太网/WLAN，看下载时是否只有 ~0.1 MB/s
2. 下载完成后看启动器有没有报失败的模组文件（有的话就是 ① 的重试问题）
3. 临时关掉 Windows Defender 实时保护 1 分钟，重新导入一次，对比「解压 100% → 开始下载」的空档是否消失
4. 复现测量脚本（我已放在项目里）：
   `node _export/_dl_bench.mjs` → 会打印 24 并发的总吞吐与成功/失败数

---

## 六、结论一句话

**这不是单纯的"启动器写得慢"：外部带宽确实只有 0.1–0.6 MB/s（单连接被限速 40 KB/s），但启动器把失败重试降成 4 并发、不换源、不分片，导致"进度 100% 后还在爬"——这部分是能修的，修完 304 MB 大约 10~15 分钟。**
