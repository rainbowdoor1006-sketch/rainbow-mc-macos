# RAINBOW MC · 插件系统（选定方案）

> 依据你的四个选择：
> ① **范围**：不改动现有启动方式、核心功能与任何现有功能，插件只做「新增」
> ② **沙箱**：双进程（utilityProcess）+ iframe UI
> ③ **分发**：本地目录 `data/plugins` + GitHub 仓库直装
> ④ **权限**：能力清单 + 运行时网关

---

## 一、总原则（按你的要求锁死）

```
✅ 插件只能「新增」能力
❌ 不能改启动参数、不能替换下载源、不能覆盖内置诊断规则、不能改现有页面
❌ 不能直接碰 config.json / library.json / 存档
❌ 不能拿到账号令牌（任何权限都不给）
```

内置功能优先级永远高于插件：

| 场景 | 规则 |
|---|---|
| 下载源 | 内置源全部失败后，才轮到插件提供的源 |
| 整合包格式 | 内置解析器认不出时，才问插件 |
| 崩溃诊断 | 内置 29 条规则先跑，插件规则只在「未命中」时追加 |
| 主题 | 插件主题属于「自定义主题」，不能覆盖内置三套 |

## 二、架构

```
┌─────────────────────────────────────────────────┐
│ 主进程 main（现有代码，完全不动）                 │
│  ├─ store / launcher / installer / cf / modpack  │
│  └─ plugin-host-manager  ← 新增：只负责拉起/转发  │
└───────────────┬─────────────────────────────────┘
                │ IPC（受限通道 plugin:*）
┌───────────────▼─────────────────────────────────┐
│ 插件宿主 plugin-host（utilityProcess，独立进程）  │
│  ├─ 插件加载器（读 manifest，校验 engines）       │
│  ├─ 能力网关（每次调用查权限，记 trace id）       │
│  ├─ 注册表（页面 / 命令 / 主题 / 源 / 规则）      │
│  └─ 每个插件独立 try/catch + 5 秒调用超时         │
└───────────────┬─────────────────────────────────┘
                │ 类型化 RPC（postMessage / MessagePort）
┌───────────────▼─────────────────────────────────┐
│ 渲染层                                            │
│  ├─ 插件页面：<iframe sandbox="allow-scripts">     │
│  │   入口 plugin://<id>/page.html（自定义协议）    │
│  └─ 宿主 UI：侧栏多出「插件页面」入口              │
└─────────────────────────────────────────────────┘
```

**为什么双进程**：插件死循环 / 崩了，主进程和游戏启动不受影响；进程被杀即可卸载干净，不留句柄。

**为什么用 iframe**：插件 UI 拿不到 Node、拿不到 preload、拿不到其它 iframe 的数据；通信只能走我们定义的 postMessage 协议。

## 三、插件目录与清单

```
data/plugins/
└─ mc-status-card/
   ├─ plugin.json        ← 清单（必须）
   ├─ host.js            ← 后端入口（可选，跑在 plugin-host 里）
   ├─ page.html + page.js ← UI 入口（可选，跑在 iframe 里）
   └─ data/              ← 该插件专属可写目录（api.fs 限定于此）
```

`plugin.json`：

```json
{
  "id": "mc-status-card",
  "name": "服务器状态卡片",
  "version": "1.0.0",
  "author": "某人",
  "description": "在启动页显示常用服务器在线状态",
  "engines": { "rainbow": "^1" },
  "permissions": ["ui:page", "net:http", "storage"],
  "main": "host.js",
  "page": "page.html",
  "contributes": {
    "pages": [{ "id": "status", "title": "服务器状态", "icon": "server" }],
    "commands": [{ "id": "status.refresh", "title": "刷新服务器状态" }]
  }
}
```

## 四、权限清单（网关逐项校验）

| 权限 | 能做什么 | 风险 |
|---|---|---|
| `ui:page` | 注册一个侧栏页面（iframe） | 低 |
| `ui:card` | 在指定位置插入卡片 | 低 |
| `theme` | 注册自定义主题（不能覆盖内置） | 低 |
| `command` | 注册命令面板动作 | 低 |
| `storage` | 读写 `data/plugins/<id>/data/` | 低 |
| `net:http` | 通过 `api.fetch` 发 HTTP（域名需在 manifest 列出，安装时展示） | 中 |
| `fs:project` | 只读当前项目的 mods/logs/config 列表与日志内容 | 中 |
| `diag:rules` | 追加崩溃诊断规则（内置未命中时生效） | 中 |
| `source:fallback` | 作为「兜底下载源」参与解析 | 中 |
| `pack:fallback` | 作为「兜底整合包解析器」 | 中 |
| `notify` | 发系统通知 / 启动器内提示 | 低 |

**没有**的权限（永远不会给）：`launch:hook`、`account:*`、`update:*`、任意路径 `fs`、`child_process`。
→ 这就是「不改现有启动方式」的技术保证：插件根本没有改启动参数的接口。

## 五、API v1（只增不改）

```ts
// 后端（plugin-host 内可用）
rainbow.plugin.manifest            // 自己的清单
rainbow.storage.get/set            // 只能写自己的 data/
rainbow.fetch(url, init)           // 受 manifest 域名白名单限制
rainbow.projects.list()            // 只读：id / name / mcVersion / loader
rainbow.projects.activeId()
rainbow.logs.read(projectId, 'latest')   // 需要 fs:project
rainbow.diagnostics.registerRules([...]) // 需要 diag:rules
rainbow.sources.registerFallback({ name, resolve })  // 需要 source:fallback
rainbow.packs.registerFallback({ name, match(ext, names), parse })  // 需要 pack:fallback
rainbow.ui.registerPage({ id, title, icon })         // 需要 ui:page
rainbow.commands.register({ id, title, run })        // 需要 command
rainbow.themes.register({ id, name, vars })          // 需要 theme
rainbow.notify(title, body)                          // 需要 notify

// 前端（iframe 内可用，通过 postMessage 桥）
rainbowUI.ready()
rainbowUI.projects.list()
rainbowUI.commands.execute(id)
rainbowUI.toast(text)
rainbowUI.setTitle(title)
```

约定：
- 所有调用带 `traceId`，日志里能追到「哪个插件的哪个调用」
- 单次调用超时 5 秒 → 中断并记警告
- 同一插件连续 2 次导致宿主崩溃 → 自动禁用并提示

## 六、安装与加载流程

```
① 放目录：把插件文件夹放进 data/plugins/
② 或 GitHub 直装：设置 → 插件 → 「从 GitHub 安装」填 owner/repo
     → 拉默认分支的 plugin.json（api.github.com contents）
     → 按 manifest 下载 host.js / page.html（或整个 release zip）
     → 展示权限清单，用户确认
③ 启动时加载：读 manifest → 校验 engines → 校验权限 → 在 plugin-host 里 import
④ 插件管理页：启用 / 禁用 / 卸载 / 查看权限 / 查看日志 / 查看 trace
```

GitHub 直装的安全提示（必须显示）：

```
⚠ 该插件来自 GitHub，未经审核。
   它申请了：net:http（可能连接 xxx.com）、fs:project（可读取你的模组列表）
   作者：owner/repo，最近更新：2026-10-24
   [取消] [仍要安装]
```

## 八、这个方案的风险（针对你的选择）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| R1 | **GitHub 直装 = 无审核入口** | 学生用户会被"免费插件"骗，装到恶意代码 | 必须显示权限清单 + 橙色警告；`net:http` 列域名；不提供任何账号 API |
| R2 | **iframe 插件体验差** | 插件页面和原生页面风格不一致 | 提供 CSS 变量与模板，主题跟随启动器 |
| R3 | **双进程启动变慢** | 每次启动多拉一个进程（约 100~200 ms） | 懒加载：只有存在插件时才拉起宿主 |
| R4 | **插件写坏自己的 data 目录** | 磁盘垃圾 | 卸载时询问是否删除插件数据 |
| R5 | **能力边界不清导致插件"越权感"** | 作者想改启动参数但 API 不给 | 文档明确写「v1 无启动钩子」，避免无效提需求 |
| R6 | **没有签名 → 分发信任问题** | 用户无法判断插件是否被篡改 | 直装时展示 commit sha + 文件 sha256；后续做签名 |
| R7 | **维护精力** | 插件 API 一改就要兼容 | 只增不改 + `engines` 版本协商 + 弃用期 |
