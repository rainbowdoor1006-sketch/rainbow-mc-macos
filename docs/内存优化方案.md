# 内存优化方案（RAINBOW MC）

> 目标：在不影响其他进程的前提下，把「能安全回收的内存」做到极致。
> 结论先放前面：**真正安全的天花板是「回收我们自己 + 清自己的缓存」**，其余方案要么需要管理员，要么会牺牲别人的流畅度。

---

## 一、已实现在启动器里的（0.2.72，按钮「优化电脑内存」）

| 动作 | 说明 | 实测效果 |
|---|---|---|
| V8 垃圾回收 | 主动 `gc()`，释放截图缓存、模组索引等大对象 | — |
| 自身工作集修剪 | `EmptyWorkingSet(自己)`，把已提交但未访问的页还给系统 | **106 MB → 10 MB**（释放 96 MB） |
| 清自身缓存 | 旧更新包、`.tmp/.part`、提权日志、7 天前的索引文件 | 1 个文件 |
| 子进程工作集修剪 | 只对「我们亲手拉起的 javaw / 陶瓦」生效，不碰别人 | 干进程时 0 个 |
| 退出时归还 | 关闭启动器前再修剪一次 | 常驻内存不再残留 |

**为什么不做「全系统内存清理」**：那类工具（含各种"内存优化大师"）大多对**所有进程**调用 `EmptyWorkingSet`。别的程序下次访问内存要重新从页面文件读回，表现就是"点一下卡一下"。这与你要求的"不影响所有进程"直接冲突，所以不做。

## 二、还能再往上加的（按风险排序）

### A 级 · 零风险，随时可加

| 方案 | 收益 | 代价 |
|---|---|---|
| 分级缓存（图片/图标 LRU 上限 64 MB） | 长期跑 8 小时后能省 100~300 MB | 无 |
| 后台标签页/隐藏页面 `webContents.setBackgroundThrottling` | 隐藏时降 CPU 与内存 | 无 |
| 日志与临时目录自动轮转（>50 MB 截断） | 长期省几十 MB 磁盘+缓存 | 无 |
| 启动器最小化到托盘后释放渲染进程缓存（`webContents.session.clearCache`） | 最小化 10 分钟后省 50~150 MB | 再次打开稍慢 0.3 秒 |

### B 级 · 低风险，需要你点一次确认

| 方案 | 收益 | 代价 |
|---|---|---|
| 把 `--max-old-space-size` 调低（默认 V8 可涨到 2 GB） | 防止启动器自己膨胀 | 超大整合包列表可能触发 GC 更频繁 |
| 联机时暂停启动器内下载任务 | 让出带宽与内存 | 下载暂停（可恢复） |
| 启动游戏后自动把启动器最小化并修剪 | 游戏期间启动器只占 10~20 MB | 无 |

### C 级 · 需要管理员，且会影响系统行为

| 方案 | 收益 | 代价 |
|---|---|---|
| 清空 Standby List（`EmptyStandbyList` / RAMMap） | 立刻让"可用内存"数字变好看 | 需要管理员；清完文件缓存会变慢，属于"数字好看但不一定更快" |
| 调整页面文件 / 内存压缩（`MemoryCompression`、`ClearPageFileAtShutdown`） | 极端低内存机器有改善 | 需要管理员 + 重启 |
| 关闭 SysMain（Superfetch） | 省 100~300 MB | 机械硬盘机器开机/启动程序明显变慢 |

### D 级 · 不建议

| 方案 | 原因 |
|---|---|
| 对所有进程 `EmptyWorkingSet` | 别人会周期性卡顿，与"不影响所有进程"矛盾 |
| 定时自动"清理内存" | 每清一次都要重新换页，长期反而更慢 |
| 关闭内存压缩 | 低内存机器会频繁读页面文件，体验更差 |

## 三、极致优化量的正确做法（不动别人）

如果目标是「同样的机器，跑 MC 更稳」，按收益排序其实不是"清内存"，而是：

1. **给 JVM 分配合适内存**（已实现：3 GB + 25 MB/模组，上限 20 GB / 55% 物理内存）
2. **JVM 参数**：`-XX:+UseG1GC -XX:MaxGCPauseMillis=50 -XX:+ParallelRefProcEnabled`（大幅减少 GC 卡顿）
3. **减少重复加载**：模组索引缓存到磁盘（已实现），二次启动省 30~60 秒
4. **启动器自身瘦身**：懒加载页面组件、图片 LRU（A 级方案）
5. **关掉不用的后台**：这个是用户自己的事，启动器不该替用户杀进程

一句话：**把「清内存」做到极致，天花板就是 A 级那 4 条 + 我们自己的 96 MB。再往上就必须碰别人的进程或要管理员。**

## 五、实测数据（0.2.73，本机 64 GB 内存）

| 档位 | 处理进程 | 可用内存变化 | 占用变化 |
|---|---|---|---|
| 优化前 | — | 25,197 MB | **61.2%** |
| 温和（safe） | 19 个 | **+2,832 MB** | 61.3% → **56.9%** |
| 极致（aggressive） | 275 个 | **+3,850 MB** | 57.2% → **51.2%** |
| 再等 2 秒后 | — | 32,539 MB | **49.9%** |

外部核对（`Win32_OperatingSystem`）：可用 32,768 MB / 总 64,898 MB → **已用 49.5%**

进程存活核对：Edge 52 个进程、explorer、dwm 全部正常，无进程被结束。

> 说明：这是「工作集回收」，不是把已提交内存真正还回系统。效果会随使用逐渐回升（进程重新访问被回收的页），
> 属于「立刻让占用下来」而不是「永久降低」。真正永久降低只能靠减少常驻程序。
