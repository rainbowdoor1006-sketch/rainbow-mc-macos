# 整合包下载 · 极限提速方案（不租服务器 / 不额外操作 / 不要管理员）

> 依据：2026-10-29 在本机对 `cdn.modrinth.com` 的实测
> 状态：**方案文档，未改任何代码**

---

## 一、先看清"物理上限"在哪

| 测试 | 结果 | 说明 |
|---|---|---|
| 单连接 | **38–43 KB/s** | 单条 TCP 被 Fastly 限速 |
| 8 个不同文件并行 | 138 KB/s | 连接数上去，吞吐上去 |
| 16 个不同文件并行 | **569 KB/s** | 空闲时的接近上限 |
| 24 个不同文件并行 | 448 KB/s，**约 40% 请求被断流** | 触发了限流 |
| 同一文件切 32 个 Range 分片 | **仅 1/32 成功，27 KB/s** | ❗分片这条路被 CDN 掐死 |

节点位置：

```
cdn.modrinth.com → Fastly 新加坡 POP（X-Served-By: cache-sin-…-SIN）
ping 79 ms，丢包明显
备用域名 cdn-raw.modrinth.com → 301 回 cdn.modrinth.com，同一个 POP，无提速
外网 DoH（Cloudflare/Google）查询超时，无法挑其它 POP
本机无公网 IPv6（只有 Teredo），走不了 v6 通道
```

**结论：天花板是"你家宽带到新加坡 Fastly 的总出口"，大约 0.15–0.6 MB/s。**
所以方案的目标不是"突破上限"，而是**把上限吃满、把等待时间压到零浪费**。

---

## 二、九条提速措施（全部满足你的四个约束）

### 1. 高并发 + 连接池（核心）

```
undici Agent：connections: 64，keepAliveTimeout: 30s
全局并发：起步 32，按「成功率 / 429 / 断流率」在 16~48 之间自适应
```

现在实际只跑出 7 条连接（实测），24 并发等于白设。
预计：把 0.1 MB/s 拉到 0.4–0.6 MB/s。

### 2. 不要分片，改为"把文件铺开"

实测同一文件切 32 片只有 1 片成功 → **CDN 对同一 object 的并发 Range 有硬限**。
正确做法：尽量让 **103 个不同文件同时处在传输中**（文件级并行），而不是切同一个文件。

### 3. 令牌桶节流（避免自己把自己限死）

```
每秒最多新开 8~12 个请求（可调），失败率 >15% 时自动降到 6
```

依据：24 并发一次性铺开时 40% 断流；节奏平稳反而总吞吐更高。

### 4. 快速失败 + 换域名重试

```
单次超时 20s（现在 600s，等于卡死 10 分钟）
重试顺序：cdn.modrinth.com → cdn-raw.modrinth.com → 原地址（新连接）
指数退避 1s→2s→4s，最多 4 次
绝不把重试并发降到 4（现在的做法，拖尾主因）
```

### 5. 阶段重叠：解压的同时就开始下载

现在：解压完 603 个文件（355 MB）→ 才开始下载 304 MB。
改为：解析完 index 立刻启动下载，overrides 在另一个线程继续解压。
省掉"解压 100% 后等几秒"的空档，也省掉解压那 10~30 秒。

### 6. 本地按 sha1 去重复用（第二大收益）

```
导入前：把 index 里 103 个文件的 sha1 拿去 data/library 和所有已有实例里查
命中：硬链接（同盘）或复制（跨盘），完全不联网
```

用户装第二个/第三个整合包时，重复模组往往占 30–70%，这一条能直接省掉。
（前提：库里已有这些文件，第一次装没得省）

### 7. 断点续传（单连接 Range）

```
每个文件记已下载字节；中断后  Range: bytes=<已有>- 续传，不重下
```

注意：续传是"一个文件一条连接顺序续"，不是并行分片（分片会被限流）。

### 8. 界面给出真实速度与 ETA

```
「已下载 123 / 304 MB · 0.42 MB/s · 剩余约 7 分钟 · 重试 3 个」
```

拖入包时先读 index 算总字节，直接告诉他"需额外下载 304 MB，预计 10~15 分钟"。
这一步不加速，但能消除"是不是卡死了"的判断成本。

### 9. 能用代理就自动用（零操作）

启动时检测系统代理（WinINET/环境变量）。如果用户已经开着 Clash 之类，就自动走代理下载；
没开就直连。用户不需要做任何新操作，只是"有快路就走快路"。

## 三、预期效果

| 场景 | 现在 | 优化后 |
|---|---|---|
| 304 MB 下载（带宽空闲） | 40–50 分钟 | **8–12 分钟** |
| 304 MB 下载（边下边用电脑） | 更久，且常常"卡在 100%" | 12–20 分钟，进度实时可见 |
| 重复导入同一系列整合包 | 全量重下 | **按 sha1 命中，可能只下 0–30%** |
| 解压到下载的空档 | 5~30 秒无反馈 | 0（阶段重叠） |
| 失败文件 | 4 并发慢慢补，可能补不完 | 32 并发 + 换域名，且给出失败清单 |

## 四、明确"不要做"的事（实测无效或有害）

| 做法 | 为什么不做 |
|---|---|
| 单文件多 Range 分片 | 实测 32 片只有 1 片成功，被 CDN 限流 |
| 找国内 Modrinth 镜像 | MCIM 302 回原站；其它镜像无响应 |
| 改用 cdn-raw 域名 | 301 回同一 POP，无收益 |
| 通过外网 DoH 挑 POP | 外网 DoH 查询超时，无法挑 |
| 走 IPv6 | 本机没有公网 IPv6（只有 Teredo） |
| 把并发开到 100+ | 触发限流，42% 断流，反而更慢 |

---

## 五、实施顺序建议

1. **P0（收益最大）**：连接池 + 自适应并发 + 令牌桶 + 快速失败换源（第 1/3/4 条）
2. **P0**：阶段重叠（第 5 条）——简单、立刻见效
3. **P1**：sha1 去重复用（第 6 条）、断点续传（第 7 条）
4. **P2**：UI 速率/ETA（第 8 条）、自动代理（第 9 条）

——全部是启动器本地逻辑，**不需要服务器、不需要管理员、不需要用户做任何额外操作**。
