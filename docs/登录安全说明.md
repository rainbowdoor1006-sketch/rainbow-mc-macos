# 登录系统安全说明（做什么能做到，什么做不到）

> 需求：其他功能可以开源，但登录系统不能被逆向分析、不能被破解。

先说结论，避免误解：**任何运行在用户电脑上的客户端程序，都不存在"绝对不可逆向"**。用户拥有二进制文件、内存和网络，理论上都能改。

所以正确的目标不是"让客户端不可破解"，而是：

> **即使客户端被改了，也拿不到有效凭证、进不了服务端。**

下面是我们已经做的、和还能做的。

---

## 一、已经做到的（这轮已实现）

| 措施 | 位置 | 作用 |
|---|---|---|
| 密码不在客户端保存 | `account:offlineLogin` | 只保留服务端签发的 token，不存密码 |
| 每次启动前强制校验令牌 | `ipc.ts` 的 `mc:launch` → `clubVerify()` | 令牌失效/封禁 → **直接终止启动流程**，弹 `E9010~E9012` |
| 校验走服务端 `/api/sso/userinfo` | `minecraft/club.ts` | 是否有效由服务器说了算，客户端无权伪造 |
| 失败也是 HTTP 200，看 `body.ok` | `club.ts` | 防止只看状态码导致判断错误 |
| 打包后关闭 devtools | `main/index.ts` | 用户无法随手 F12 改状态 |
| 屏蔽 F12 / Ctrl+Shift+I / Ctrl+R | `main/index.ts` | 同上 |
| 禁止页面被外部链接导航 | `main/index.ts` | 防钓鱼替换页面 |
| ASAR 打包 | `electron-builder` | 提高解包门槛（不是加密，可解） |
| 不打印 token | 全项目日志 | token 等同密码 |

## 二、必须理解的两个边界

### 1. 客户端"跳过校验"能做什么？

有人把 `mc:launch` 里的 `clubVerify()` 删掉，然后启动器照常启动**离线版 Minecraft**。

**这件事我们拦不住**，因为离线版 Minecraft 本身不需要任何账号——它是纯本地游戏。

### 2. 那"破解"到底危害什么？

真正有价值的资产在服务端：

- 社团网站账号、社区身份、排行榜、服务器白名单
- 以后基于 `user.id` 的任何权限

这些**永远由服务端判定**。客户端被改，最多是"自己骗自己"，拿不到任何服务端资源。

**所以不要把"阻止别人玩离线 MC"当作安全目标——目标应该是"阻止别人冒用社团账号"。** 这个我们已经做到了：token 只能由服务端签发，客户端不会保存密码，改代码也变不出有效 token。

## 三、还能加的三层（按性价比排序）

### 层 1：服务端绑定（最有效，需要网站侧配合）

在 `launcher-auth` 成功时，把下面的信息一起入库：

```
token 绑定：user_id + 设备指纹 + 签发 IP + 启动器版本
```

设备指纹由客户端算：`SHA256(主板序列号 + Windows MachineGuid + 首个网卡 MAC)`，随请求发 `device_id`。

服务端在 `/userinfo` 时校验 `device_id` 是否一致，不一致就 401。

**效果**：token 被偷走后，换台机器用不了。

### 层 2：短时令牌 + 静默刷新（防长期盗用）

- 把 30 天 token 改成分两层：`access_token`（2 小时）+ `refresh_token`（30 天）
- 每次启动拿 refresh 换新的 access
- 用户可以在网站「授权管理」一键撤销

**效果**：被盗的 token 最多用 2 小时。

### 层 3：代码保护（提高逆向成本，不是绝对安全）

| 手段 | 说明 | 代价 |
|---|---|---|
| `bytenode` 编译核心模块 | 把关键 JS 编译成 V8 字节码，`asar extract` 后看不懂 | 构建复杂，调试变难 |
| `javascript-obfuscator` | 变量名混淆、字符串加密、控制流平坦化 | 体积变大，可能影响性能 |
| 原生插件（.node） | 把校验逻辑写成 C++ 编译 | 要写 C++，跨平台麻烦 |
| 代码签名 + 完整性校验 | 检测 exe 是否被改 | 需要证书 |

**建议**：只对 `club.ts` 和启动校验那段做混淆，其他保持可读（你要求其他功能开源）。

## 四、仓库拆分建议（配合"其他功能开源"）

```
rainbow-mc/                 ← 开源（MIT）
  app/src/...               ← 除下面这个模块外全部
  LICENSE

rainbow-mc-auth/            ← 闭源，只发编译产物
  src/club.ts               ← 授权逻辑
  src/launch-guard.ts       ← 启动前校验
  build/                    ← 打包进主程序前先混淆
```

主仓库里用 `file:../rainbow-mc-auth` 引用，发布时把混淆后的产物拷进 `app/node_modules`。

这样：
- 别人能看你启动器 90% 的代码（符合"开源"）
- 登录模块只有混淆产物
- **真正的防线仍然是服务端**

---

## 五、一句话给「登录系统不能被破解」

> 我们保证：**没有有效社团账号，就拿不到能通过的 token；token 被改、被换机器、被封禁，服务端立刻拒绝。**
> 我们不能保证：**别人改客户端后不能自己玩离线 MC**——这属于本地游戏的固有属性，除非做成纯在线验证（每次启动必须联网拿许可），而那会牺牲可用性。

如果你要更硬的方案，只有一条路：**每次启动都必须向服务端换取一次性启动票据，票据 5 分钟有效、绑定设备、用一次作废**。需要网站侧加接口，我这边可以配合实现。
