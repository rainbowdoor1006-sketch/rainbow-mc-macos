# 整合包导入 · 进度回退与卡顿问题（待修）

> 记录时间：2026-10-31　版本：0.2.81
> 状态：**仅诊断，未修改**；下载/安装仍在运行中，未打断
> 触发场景：导入 `七七的小翔修仙世界低配版 0.2.100beta.mrpack`（103 个文件 / 304 MB）

---

## 问题一：进度会倒退（90% → 70% → 9% → 7%），速度骤降到几十 KB/s

### 现象

1. 下载进度到 90% 左右，突然**倒退到 70%**
2. 继续下载到 90%+ 又退到 **9%**，再退到 **7%**
3. 每次倒退后速度掉到 **几十 KB/s**，之后又慢慢爬升

### 现场证据（实例 `5d4753aa`）

```
[自然音效] AmbientSounds_FORGE_v6.3.11.jar   8 个 .seg，已下 47.19 MB（文件约 51 MB）
[现代化 UI] ModernUI-...-universal.jar       8 个 .seg，已下 22.96 MB（文件约 24 MB）
+ 两个 0 字节的 .part 文件
界面：83.7% · 254.3/304.0 MB · 52 KB/s
连接数：18（最高 48）—— 大量 worker 在重试
```

即：两个大文件已经下到约 90%~96%，但其中**某一段失败 → 整份被判失败 → 回退单连接从 0 重下**。

### 根因（代码位置）

**① 进度统计不是单调的** — `http.ts` `downloadAll`

```ts
onBytes: (loaded) => { live.set(myIndex, loaded); reportLive() }
```

进度 = 已完成字节 + 各任务「当前已下字节」。
某任务重试时 `loaded` 归零 → 总数立刻下降 → 进度倒退。

**② 分段失败后整份作废，已下的段不复用** — `http.ts` `downloadOne`

```ts
if (mb >= 8) {
  const seg = await downloadSegmented(...)   // 任一段失败 → return null
  if (seg) return seg
}
// 回退：写 .part，从 0 开始单连接
```

`downloadSegmented` 失败时保留了 `.seg`（本意是续传），**但回退路径根本不读它们**。
实测一个文件白下 47 MB、另一个白下 23 MB。

**③ 单连接回退也不续传**
`.part` 从 0 开始，且单连接只有约 40 KB/s → 这就是“速度突然掉到几十 K”。

**④ 8 段 × 48 在途仍会踩到 CDN 限流**
两个文件都卡在分段阶段，说明并发一高 CDN 就断流/超时（空闲 20 s 判失败），
一个文件只缺 1 段也整份作废 → 回到 ②③。

### 修复方案

| 优先级 | 改动 | 位置 | 预期 |
|---|---|---|---|
| P0 | 进度取**高水位**：`reported = Math.max(reported, current)`；「重试中 N 个」单独显示，不参与主进度 | `http.ts` `downloadAll` | 不再倒退 |
| P0 | 分段失败**先补缺的段**（`Range` 从已有 `.seg` 续传），连续失败 3 次才降 4 段、再失败降 2 段 | `http.ts` `downloadSegmented` | 不再浪费已下流量 |
| P0 | 单连接回退也续传：用已有 `.part` 大小作为 `Range` 起点 | `http.ts` `downloadOne` | 降级不重下 |
| P1 | 在途请求 48 → 32；遇 403/429/断流**动态降到 24** | `http.ts` | 减少触发限流 |
| P1 | 记录失败原因（HTTP 码 / idle timeout / 断流）到日志 | `http.ts` | 可定位 |
| P2 | 结束时清理 `.seg/.part` 残留，并报告「本次浪费 X MB」 | 导入收尾 | 磁盘干净 |

### 验收标准

- 同一 mrpack 导入全程进度**单调不减**
- 分段失败后，已下载字节不重复下载（对比 CDN 侧流量）
- 304 MB 总耗时 ≤ 8 分钟（当前正常段实测 7 分 07 秒）

## 问题二：卡在「正在安装加载器… 处理中… 0 B/s」好几分钟

### 现象

```
正在安装加载器…
预取 Forge 依赖 16/36
…  处理中…  0 B/s
```

进度条空、速度恒为 0，看起来完全卡死，实际持续数分钟。

### 现场证据

```
实时下行：102 KB/s（并没有停）
最近写入：libraries/net/minecraftforge/fmlcore/…jar、guava-25.1-jre.jar.part(0 字节) 等
界面文字：预取 Forge 依赖 16/36
```

**它其实在下载 Forge 依赖库，只是界面拿不到字节数。**

### 根因

**① `loader` 阶段不报字节**
`pack:progress` 的 `loader` 阶段只带 `name` 文本（`预取 Forge 依赖 16/36`），
不带 `done/total` 字节 → 前端算不出速度 → 恒显示 `0 B/s`、进度条停在 0。

**② 预取并发偏低**
`loaders.ts` `prefetchForgeLibraries` 用 `downloadAll(tasks, { concurrency: 8 })`，
Forge 依赖多是几十 KB ~ 几 MB 的小文件，每个文件单连接（30~100 KB/s），
36 个文件分 5 轮，每轮几十秒 → 自然要几分钟。

**③ 单批 25 秒看门狗会放弃慢批次**
超时的批次被丢弃，改成让 **Forge 安装器自己**去下（单线程、更慢、且我们也没有它的进度）。

### 修复方案

| 优先级 | 改动 | 位置 |
|---|---|---|
| P0 | `loader` 阶段补字节进度（预取时把已下字节数上报给 UI），显示「预取 16/36 · 3.2 MB / 12 MB」 | `loaders.ts` + `ipc.ts` |
| P0 | 预取并发 8 → 16（小文件多，靠连接数换吞吐） | `loaders.ts` |
| P1 | 25 秒看门狗改为「整体 90 秒 + 单文件 20 秒」，避免整批被砍 | `loaders.ts` |
| P1 | 预取失败时明确提示「将改用安装器自行下载，会慢一些」 | `ipc.ts` |
| P2 | 若安装器在跑，解析其 stdout 里的 `Downloading …` 行，映射成进度 | `loaders.ts` |

### 验收标准

- 安装加载器阶段**进度条与速度都在动**
- 同一 Forge 版本（1.20.1-47.4.23）预取耗时 ≤ 60 秒
- 界面不出现「0 B/s 持续 > 10 秒」而无任何文字变化

---

## 附：影响面

- 问题一影响**所有含 ≥8 MB 模组的整合包**（大包几乎必现）
- 问题二影响**所有 Forge / NeoForge 首次安装**（Fabric 走 profile，不受影响）
- 两者都不影响最终安装结果，只影响体验与耗时（实测同一包 7 分钟 → 20 分钟以上）

## 修复状态（2026-10-31，0.2.82 已实现并实测）

### 问题一：已修

| 改动 | 实现 |
|---|---|
| 进度单调 | `downloadAll` 改为按「每个任务的历史峰值」汇总，重试归零不影响总进度；新增 `onRetry` 提示重试数 |
| 分段失败不重下 | 单段带重试（4 次，从已有 `.seg` 续传）；整体失败走 `resumeFromSegments`：预分配 `.part` → 合并已下段 → 只补缺口 |
| 单连接也续传 | 回退路径用 `Range: bytes=<已有字节>-` 追加，不从头下 |
| 限流自适应 | 在途 32（原 48），连续失败 6 次自动降到 16~24 |
| 失败可查 | 失败原因写 `data\logs\download.log` |
| 收尾清理 | 成功后删除 `.seg`；导入结束无残留 |

### 问题二：已修

| 改动 | 实现 |
|---|---|
| loader 报字节 | 预取 `downloadAll` 增加 `onProgress/onLiveBytes`，ipc 把 `done/total` 透传给界面 |
| 预取更快 | 改为一次性铺开、并发 16（原分批 16+每批 25 s 看门狗） |
| 看门狗放宽 | 25 s → 180 s，慢镜像不再整批被砍 |
| 界面不再假死 | `DropImport` 在 loader 阶段有字节时显示真实百分比与速度 |

### 实测（同一 mrpack，304 MB）

| 指标 | 修复前 | 修复后（0.2.82） |
|---|---|---|
| 总下载耗时 | 12m50s（严重时 20~30 分钟） | **3m04s** |
| 进度回退 | 90%→70%→9%→7% | **全程单调，无一次回退** |
| 平均速度 | 约 490 KB/s（回退时掉到几十 KB/s） | **约 2.0~2.5 MB/s**（尾段自然下降） |
| 临时残留 | 24 个 `.seg/.part`（225 MB） | **0** |
| 失败重试记录 | 大量 | **0**（`download.log` 未产生） |
| 结果完整性 | 119 jar | 119 jar / 328.6 MB，Forge 47.4.23 已装好 |

> 说明：本次测速未触发分段失败，因此「补洞续传」路径未被实际执行；该路径已按逻辑实现，后续遇到限流时才会走到。
