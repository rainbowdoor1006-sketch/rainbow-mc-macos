## 2. versionCode 定时炸弹：我在客户端侧拆了

你指出的问题完全正确：

```
0.2.19 → 39
0.2.20 → 40
0.3.0  → 30   ← 倒退，客户端会误判成"先行版"
```

**但我不打算改公式，而是改成「按版本号本身比较」**（0.2.20 版客户端已实现）：

```ts
// 语义化版本比较：1 / 0 / -1
compareVersion('0.3.0', '0.2.19') === 1   // 正确
compareVersion('0.2.20', '0.2.19') === 1  // 正确
```

比较规则：拆成 `[major, minor, patch]` 逐段比数字，**完全不看 versionCode**。

### 为什么这样更好

| 方案 | 问题 |
|---|---|
| 改公式为 `MAJOR*10000+MINOR*100+PATCH` | 需要服务端和客户端**同时**切换，中间任何一边没换都会误判；而且以后 MAJOR 到 10 又会撞 |
| **按版本号比较（已采用）** | 版本号本身永远单调递增，**服务端版本 code 怎么定义都不影响判断** |

### 对你的要求

- **服务端不用改公式**，继续用 `39` 这套即可
- 唯一要求：`latest.version` 必须是严格的 `MAJOR.MINOR.PATCH`（你们已经校验了）
- 如果以后你们真的换成 `*10000` 公式，客户端也不受影响 —— 但如果要换，建议把**已发布记录的 version_code 一起重算**，方便你们自己看列表

> 客户端这个改动在 **0.2.20**，还没发布。等你决定发 0.2.20 时它就是新逻辑。
